# Pass 3 (Revised): Cleaned Output Integrity (`utils/jsonOptimize.ts`)

## Context

Tutorial Dissector produces two output formats:
- **Raw JSON** — flat arrays of `narrative_steps`, `visual_actions`, `video_annotations` with foreign key references (`linked_visual_action_ids` on each step pointing to action IDs)
- **Cleaned JSON** — nested structure where each step contains its actions inline, with pipeline-internal fields stripped (IDs, `confidence`, `spatial_bounding_box`, `ui_context`, `chunkIndex`)

The cleaned format is generated by `cleanFinalOutput()` in `utils/jsonOptimize.ts` (lines 97-188). It runs server-side after Phase D completes (`server/jobManager.ts:614`) and is stored in `state.cleanedOutput`. The function resolves foreign keys by looking up each `linked_visual_action_ids` entry in an action map and embedding the full action object inside the step. It then strips IDs from both steps and actions (since the nesting makes them unnecessary).

## Defects Fixed

| Issue | Root Cause |
|---|---|
| Cleaned output contains duplicate actions. When two narrative steps reference the same action ID (multi-linked), the action is physically embedded in both steps. Since IDs are stripped afterward, consumers can't detect the duplication. Recent output: 107 total actions vs ~81 unique. | `cleanFinalOutput` inlines every `linked_visual_action_ids` reference without tracking ownership. |
| Cleaned output can have timestamp regressions (step N+1 earlier than step N). | `cleanFinalOutput` preserves step ordering from raw input without sorting. |

## Critical Review of Original Prompt

The original prompt had the following issues that this revision addresses:

### Critical

1. **Insertion point sequencing bug**: The original specified inserting ownership code "after the destructuring" (line 104/105), but the code requires `actionMap` which isn't created until line 106. Inserting literally as directed would crash at runtime with a `ReferenceError`. The correct insertion point is **after line 111** — after `actionMap`, `annotationMap`, `linkedActionIds`, and `linkedAnnotationIds` are all created.

2. **Two redundant inline timestamp parsers instead of importing existing tested utility**: The original defined `parseTs` (for the sort comparator) and `parseTime` (for the ownership block) as two separate inline functions that do the same thing. Meanwhile, `parseMMSS` already exists in `utils/timeUtils.ts`, is imported by 4 other files, handles all the same cases *plus* raw-seconds strings and `.trim()`, and has unit tests in `utils/timeUtils.test.ts`. The prompt should import and use `parseMMSS`.

### High

3. **O(steps × actions × steps) performance in ownership assignment**: The ownership algorithm used `sortedNarrativeSteps.find(s => s.id === existingOwner)` — a linear scan per comparison inside a nested loop. For 50 steps and 200 actions this is ~10,000 unnecessary find calls. Fix: pre-compute a `Map<string, number>` of parsed step timestamps for O(1) lookups.

4. **No tests exist or are required**: The original prompt introduced non-trivial behavioral changes (sorting, ownership-based deduplication) to a function with zero test coverage, without requiring any tests. A regression here would silently corrupt exported output. Tests should be mandated.

5. **Missing/empty timestamps silently produce dist=0**: If both a step and an action have empty/missing timestamps, `parseTime("")` returns 0 for both, giving `dist = 0`. This gives the first empty-timestamp step maximum ownership priority over all empty-timestamp actions, potentially concentrating them into a single step. The prompt should document this edge case and the desired behavior.

### Medium

6. **Tie-breaking semantics unspecified**: When two steps are equidistant from an action (`currentDist === existingDist`), the original prompt's code keeps the action with whichever step was processed first. Since steps are sorted by timestamp, this means the earlier step wins — but this was an accident of iteration order, not an explicit design choice. This revision explicitly documents: "earlier step wins on ties."

7. **Pre-existing `parseTime` duplicate in `detectUnlinkedActions` not consolidated**: Lines 259-265 of `jsonOptimize.ts` already contain an inline `parseTime` that duplicates `parseMMSS`. Since the prompt is already touching this file and introducing timestamp parsing, it should consolidate all parsers into a single import. Leaving three near-identical timestamp parsers in one file is a maintenance hazard.

8. **Annotation deduplication not considered**: `linked_annotation_ids` has the exact same structural multi-linking problem as actions — multiple steps can reference the same annotation ID. The original prompt didn't address or acknowledge this gap. This revision explicitly notes it as a known gap and explains why it's acceptable for now.

### Low

9. **Shadow variable risk**: The original `narrativeSteps` parameter remains in scope alongside `sortedNarrativeSteps`, making it easy for an implementer to accidentally reference the unsorted variable. Implementers should be warned to only use `sortedNarrativeSteps` after its creation.

10. **Confusing self-analysis of `linkedActionIds` correctness**: The original prompt spent significant text arguing that `linkedActionIds` tracking remains correct after the filter, with convoluted reasoning that could mislead implementers into thinking there's a subtle bug. The revised approach sidesteps the issue entirely with a simpler design (see Implementation §4).

## Revised Implementation

**Files modified:** `utils/jsonOptimize.ts` only (same scope as original). All changes inside `cleanFinalOutput`, except the `parseTime` cleanup in `detectUnlinkedActions`.

### 1. Import `parseMMSS` from `timeUtils.ts`

At the top of `utils/jsonOptimize.ts`, add to the existing imports:

```typescript
import { parseMMSS } from './timeUtils';
```

This replaces all inline timestamp parsers. `parseMMSS` handles `"MM:SS"`, `"HH:MM:SS"`, raw seconds strings, and trims whitespace. It is already unit-tested in `utils/timeUtils.test.ts`.

**Bonus cleanup**: Also replace the inline `parseTime` inside `detectUnlinkedActions` (lines 259-265) with `parseMMSS`. This is a no-behavior-change refactor since `parseMMSS` is a strict superset (it also handles single-number strings and trims). Replace all `parseTime(...)` calls in that function with `parseMMSS(...)` and delete the `parseTime` declaration.

### 2. Add sort + ownership computation

**Insert after line 111** (after `linkedAnnotationIds` initialization, NOT after the destructuring):

```typescript
  // --- Defensive sort: ensure steps are in timestamp order ---
  const sortedNarrativeSteps = [...narrativeSteps].sort((a, b) =>
    parseMMSS(a.timestamp) - parseMMSS(b.timestamp)
  );

  // --- Assign each action to exactly one step (closest timestamp wins) ---
  // Prevents physical duplication when multiple steps reference the same action.
  const actionOwnership = new Map<string, string>();

  // Pre-compute parsed timestamps for O(1) lookup during ownership resolution
  const stepTimestampMap = new Map<string, number>(
    sortedNarrativeSteps.map(s => [s.id, parseMMSS(s.timestamp)])
  );

  for (const step of sortedNarrativeSteps) {
    const stepTs = stepTimestampMap.get(step.id) ?? 0;
    for (const actionId of (step.linked_visual_action_ids || [])) {
      const action = actionMap.get(actionId);
      if (!action) continue;

      const actionTs = parseMMSS(action.timestamp);

      const existingOwner = actionOwnership.get(actionId);
      if (!existingOwner) {
        actionOwnership.set(actionId, step.id);
      } else {
        const existingTs = stepTimestampMap.get(existingOwner) ?? 0;
        const existingDist = Math.abs(existingTs - actionTs);
        const currentDist = Math.abs(stepTs - actionTs);
        // Strict < : on ties, the earlier step (processed first) keeps ownership
        if (currentDist < existingDist) {
          actionOwnership.set(actionId, step.id);
        }
      }
    }
  }
```

**Key improvements over original prompt:**
- Uses `parseMMSS` (tested, robust) instead of two inline parsers
- Uses `stepTimestampMap` for O(1) lookups instead of `.find()` (O(n))
- Explicitly documents tie-breaking: earlier step wins on equal distance
- Insertion point is correctly specified after `actionMap` exists

While technically correct (the owning step would eventually add it), that design was fragile and required pages of justification. This version is explicit and obvious: **referencing** an action marks it as linked; **ownership** only controls inlining.

## What This Revision Does NOT Address (and why)

- **Annotation deduplication**: `linked_annotation_ids` has the same multi-linking potential, but annotations are lightweight metadata (title cards, overlays) and duplication there is cosmetically harmless. If it becomes a problem later, apply the same ownership pattern.
- **Downstream order dependence**: `jobManager.ts:614` passes `cumulativeNarrative` which accumulates steps in chunk-processing order. Since chunks are processed in time order and Phase C synthesizes steps from time-windowed segments, the input is already ~sorted. The defensive sort is a safety net, not a reorder.

## Verification

After implementation:

1. **No duplicate actions:** Total actions across all steps equals unique action count. Check by signature: `${action.timestamp}|${action.action_type}|${action.detail}` — no signature should appear more than once.
2. **Step monotonicity:** `steps[i].timestamp <= steps[i+1].timestamp` for all consecutive pairs (compare via `parseMMSS`).
3. **No orphaned actions lost:** The `unlinked_actions` array should contain any actions not referenced by ANY step (same as before). Multi-linked actions are now inlined in exactly one step but still excluded from `unlinked_actions`.
4. **Action count preserved:** `sum(step.actions.length for all steps) + unlinked_actions.length + error_recovery_count === total_actions`.
